# 唤醒预约结果与中断恢复

## 问题

主动联系在领取预约时设置 `paused=true`，原面板因此会把正在执行的唤醒显示为暂停。自主探索的面板也没有区分明确暂停、正常结束未预约和中断，并始终说明会在三小时后续约；启用内部状态的助手实际上不会自动续约。

连续性助手中断后保持暂停是既有边界。主动联系仍保留原时间，自主探索却在领取时删除原时间，无法准确呈现或恢复这一明确安排。工具保存成功后的活动展示索引异常，还会令 `companion_schedule` 返回失败，容易使调用方重复实际已成功的操作。

上传日志中的 `companion_schedule` 记录均为历史消息序列化。实际工具分派没有本轮预约调用或预约失败；22:51 的唤醒在收到模型响应前被取消，不能据此说它已经尝试设置下一次。

## 修改

- 预约状态明确区分 `running`、`scheduled`、`paused`、`not_scheduled`、`interrupted`。探索还保留 `disabled`。
- 工具回执与面板展示实际状态、可执行的 `next_at`、是否可恢复。探索活动也记录安排回执，并注明其独立于主动联系。
- 探索领取时仅保留明确预约的原时间和目的。正常结束、明确暂停或另立新预约不会保留旧计划的恢复入口。
- 中断后不自动重跑。现有面板按钮在有可恢复计划时显示“恢复中断的原预约”；点击后沿用原时间与目的，仍受功能开关、空闲条件和探索每日额度控制。恢复的轮次提醒先核对已经完成的操作。
- 未启用内部状态的助手沿用既有调度规则；本次没有新增周期、重试次数或默认续约时间。
- 预约原子保存成功后，展示索引或展示日志失败单独记入应用日志，不把实际成功改报为失败。工具仍透传协程取消。

## 对接

`CompanionSchedule.status(data)` 在原预约字段外返回 `schedule_state`、`running`、`can_resume` 和 `next_at`。`ExplorationStore.status(role)` 新增相同字段，并提供 `self_paused`、`interrupted_plan` 与 `continuous`。

`paused` 是旧存储字段，在领取中的预约也可能为真；展示与收尾日志应使用实际状态，不能仅凭这个布尔值认定主动休息。探索运行中可以另有下一次预约，这时 `running=true` 且 `next_at` 有值。

## 验证

新增纯策略回归覆盖运行、完成未预约、明确暂停的区别；中断保留原时间和目的；显式恢复与每日上限；新安排和明确暂停优先于旧回合；初始自动机会不能冒充可恢复的主体安排。

现有回归继续覆盖旧票据、重复恢复、独立助手、设置撤销和既有非连续性调度。完整 Android JVM 测试随本次发布验证执行。
