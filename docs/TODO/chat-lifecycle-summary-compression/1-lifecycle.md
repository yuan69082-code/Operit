# 发送、取消与活动归属

## 已确认的问题

用户日志中 22:51 的主动唤醒等待远端响应，22:55 被取消；23:04 和 23:05 的普通用户消息已保存，但在 `ActivityNotes.begin` 报“此窗口已有活动”，未发出新模型请求。

旧代码只等待发送协程取消，没有等待主动判断协程释放活动租约；主动判断仅观察成功文本与 Error，取消时的 Idle 不会结束等待。另有 IO 返回时的及时取消窗口：活动已登记，但调用者尚未取得引用，因而无法在自己的 finally 释放。

## 修复

- 先按引用身份取得活动租约，再写记录；准备异常或取消立即释放。相同触发 ID 的旧引用不能释放新租约。
- 用户插话等待发送取消和后台判断的 finally 都完成，重复交互保留尚未结束的清理屏障。
- 发送 job 采用先注册后启动；从配置、附加信息、用户消息保存到回复收尾均进入异常边界。启动前取消也会释放 busy，并向唤醒等待者发送真实失败原因。
- 主动唤醒取得独立成功/失败通知，取消不会被转成空成功回复。最终回复保存完成才通知成功。
- 旧 collector 和旧 finally 受回合 ID 约束，不得覆盖下一轮状态。回复保存异常保留为失败，不伪装成成功。
- 本轮 token 在释放 busy 前捕获并计账；完整下一轮窗口预估放到可取消的后台 job。发送新消息、取消或摘要会停止旧预估，结果也校验轮次归属。

## 验证与边界

活动租约、清理屏障、实际 delegate 的准备失败/取消/后续发送以及 token 计账均有定向回归。完整构建和测试沿用仓库 Android JVM、Android 包及 Windows 流水线。

日志还显示远端首响应曾等待约 20～118 秒，另一次在等待约 284 秒后被取消。生命周期修复消除本地残留占用和无关预估等待，不保证远端模型响应速度。原聊天和工具操作不自动重发。
