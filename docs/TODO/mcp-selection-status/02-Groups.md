# 群聊控制与连续发言

本步骤接续 MCP 修复，统一留在本地，整批问题完成后再测试、构建、推送和发布。

- 来源信息不再作为助手正文；读取旧记录时移除旧版生成的重复来源前缀，保留不可变作者 ID。
- 每位成员使用自己的模型配置，群页面不再要求统一模型；单个成员配置失败不阻塞其他成员。
- 持续讨论只依据明确接话请求延续；安静不产生气泡，等待用户和结束会清空后续队列。
- 用户和主助手可禁言单人、多人或全员；游戏规则单独控制公开发言，结束游戏不遗留系统禁言。
- 群待办记录作者、接手人、状态、已完成内容和下一步，支持界面与工具。
- 私聊内可发现已有群、提交以自己身份发送的公开消息；持久队列在空闲时发出，离群和禁言时不得发送，不转发私聊历史。

兼容已发布版本，保留群、聊天、作者、记忆和模型配置。验证重点包括重复前缀、安静与等待、混合模型、权限、游戏禁言、待办归属和跨会话投递。

实现位置：`GroupTurnPolicy` 管理明确的接话和退出决定；`GroupReplyGate` 在公开前判定安静、禁言与成员身份；`GroupProvenance` 保留作者信息；`MessageCoordinationDelegate` 按成员解析独立模型。来源前缀只在读取和构造请求时清理，不改写历史原件。

普通群消息给选中成员各一次回应机会，明确的 `respond` 才继续邀请其他成员；`wait_user` 和 `end` 立即结束本次队列。模型也能在末尾给出 `group_turn` 控制标记，工具结果和代码块里的同名示例不能控制队列。安静决定会阻止本轮公开正文、通知和朗读。为避免先说出“我等着”再决定安静，群回复在完整决定后统一发布；这改变了群聊的逐字流式显示时机。

私聊投递使用 `group_chat groups/send`，按执行身份检查已有群成员资格。持久队列以固定消息时间戳避免进程恢复时重复插入；实际投递时重新检查成员和禁言。日常后台投递及群待办在游戏结束后处理，避免被游戏的行动顺序替换。

界面增加禁言、群待办及成员模型设置。普通文本不依赖群页面模型；附件格式化仍沿用首位成员的媒体处理配置，混合媒体能力的适配留在统一设备验证中检查。
