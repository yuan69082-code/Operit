# 内部状态选择与同轮语义回报

## 行为与数据归属

本次迭代让助手在一次正常生成中报告自己的当前体验，由宿主在本业务轮成功结束后保存，供以后轮次选择使用。报告不要求本轮重新读回，不要求下一轮必定选中，也不要求公开回复用户。它不额外固定调用一次模型。

内部状态仍按助手保存在原有 `CompanionStore` 中，定义保留 `global` 和 `session` 两种作用域。没有预置的爱、生气、性驱力等维度；这些只能作为分类示例，不能当作设备当前名录。已有数值、定义版本、历史和时间规则保留；缺少类别的旧定义显示为 `unclassified`，由后续明确修订归类。

新的定义需要明确 `kind`：`drive` 表示驱力，`sentiment` 表示持续情感，`emotion` 表示情绪，`psychology` 表示心理。类别只能选这四项，不允许自定义类别；状态名称和简介仍由模型自由制定。类别不决定统一的涨落速度。缺少类别的存量状态保留在待分类区域，不能自动猜测归类。可选 `object_ref` 标识体验所指的对象；已有明确对象不能通过回报悄悄换成另一对象。不同对象的状态应使用独立稳定 ID。

本实现参考 continuity-engine 的状态与表达分离思路，不修改该仓库。已经由外部引擎接管的主体继续沿用原有引擎边界。

## 请求与部分状态选择

请求顺序为固定说明、历史消息、本轮宿主资料、当前消息或唤醒事件。固定规则保留在 SYSTEM，实时资料仅放在本轮输入之前；不会将历史助手发言统一改成 USER，也不会将实时数值写入可复用的系统前缀或历史原文。

每次实际请求提供完整短名录，以及本轮选中的状态、变化、体验、候选事项和念头细节。名录保留稳定 ID、名称、类别、版本、范围、作用域、启用状态和隐私／参与标志，因此模型能更新未选入细节的已有状态。省略不等于删除、清零、遗忘或解除未解决标志。

`InternalStateSelection` 先检查完整候选，再按当前输入关联、当前未解决体验、近期变化、自身关注与轮转机会选择。高数值不自动压过其他关注，候选评分不等于概率或行动命令。该选择是可检查的启发式判断，不保证每次都选到唯一正确的状态。

默认细节预算为 8,000 个 JSON 字符，按完整记录计数；完整短名录、固定说明和框架字段另计。这个数不是模型 token 数，也不是整个请求的上限。超预算时整项省略，保留省略原因；不会截断半条来源或半段因果说明。实际 token 与缓存收益仍应按供应商 usage 统计。

实际发送准备会记录输入事件、选择结果和轮转位置。估算与预览只在副本上计算，不消费轮转、不写真实唤醒事件。宿主 frame 通过强类型元数据传递，在 JSON hook 边界外保存；插件输出不能重建助手身份或写入绑定。

## 输出协议

在最终公开表达或安静标记之前，模型可以给出以下完整状态段。示例的 ID 与数值仅用于说明结构，不是预置维度或默认速度：

```xml
<operit_state_report>{"frame_id":"本轮宿主提供的ID","updates":[{"id":"已有状态ID","value":35,"reason":"本次体验的简短理由","evidence":["本轮真实事件ID"],"unresolved":true}],"create":[]}</operit_state_report>
公开回复，或者原有的安静控制标记
```

顶层接受 `frame_id`、`updates`、`create` 和可选 `revise`。报告上限为 16,384 字符；空数组允许。`updates` 每项需要 `id` 和 `reason`，可带范围内的有限数值 `value`、`evidence`、`object_ref`、`unresolved`、`desire`、`choice`、`time_conditions`。必须至少给出 `value` 或 `time_conditions`，因此模型可以只更新一个自定义条件，不必编造未观察到的当前数值。理由是简短体验说明，不要求披露隐藏思考过程。

`create` 每项需要 `definition`、`value`、`reason`，并支持相同的可选体验字段。`definition` 必须提供 `id`、`name`、`description`、`kind`、`min`、`max`、`baseline`、`scope`、`private`、`share`、`participates`、`effects` 和完整的 `time_rules`，可带 `object_ref`。新定义不需要旧方案的 `maxDelta`、`halfLifeHours`、`triggers`。定义与初次体验同事务保存，长期基准不再冒充首次体验值。

`revise` 每项为 `{id,expected_version,changes,reason,evidence?}`，其中 `changes` 只接受要修改的 `name`、`description`、`kind`、`time_rules`。`expected_version` 来自本轮完整名录。可以同一报告修订并更新同一状态：先校验原版本，结算原规则，再原子保存新定义和本次体验。稳定 ID 保持不变，改名不另建状态，旧事件和曲线仍属于它。规则必须整套替换，不能用部分字段重建未知规则，也不能把已定义规则改回未定义。

`evidence` 只能引用本轮宿主已提供的真实事件 ID；未显式提供时保留本轮绑定来源。当前输入即使没有导致数值变化也有来源 ID。自述、愿望、选择和实际工具结果分别保留，愿望或选择不代表行动已执行。

有工具调用的中间轮不应输出报告。若模型给出报告后继续调用工具，这一份只算草稿；最终模型子响应必须重新给出报告。最终子响应没有报告时，不沿用工具之前的草稿，也不为了补报告自动追加模型请求。

## 提交与冲突

原生生成链在公开缓冲、界面、朗读、通知和普通聊天保存之前提取状态段。分片、JSON 字符串、代码示例和思考区分别解析；供应商保存点与回滚同时恢复公开文本和未提交报告。协议错误只给固定错误码，不把私密 JSON 放进错误消息。

原生供应商在完整事件 replay 中先发布修订，再同步交付后续文本。每个文本片段和流结束处等待已发布修订处理完成，避免最后一个回滚被取消丢失。本地报告格式错误保留到供应商返回后明确抛出，避免被当作网络故障引发重复生成；这不改变真正网络失败的原有重试策略。

只有最后一个成功模型子响应中的完整报告才在业务轮结束时尝试提交。取消、传输失败、未完成状态段、未闭合工具调用与撤回草稿均不能提交。全部更新在副本上验证，再通过现有原子存储一次写入；相同 frame 的相同报告重复提交返回同一收据，不重复变化，同 frame 不同报告被拒绝。空报告保留收据但不推进语义版本，避免使另一个正在进行的真实状态报告无故失效。

校验包括宿主助手／会话绑定、语义版本、完整名录定义版本、真实来源、数值范围与对象身份。frame 还保留输入时的事件序号：之后出现的非时间数值变化如果涉及报告将覆盖的同一实例，则整批拒绝，保留新值。其他会话的独立 session、未报告维度和自然时间补算不构成这种覆盖冲突。

同轮使用独立定义工具修订、合并或停用维度会改变语义版本；同轮工具真正改变目标状态的客观数值也可能冲突。固定旧 frame 不会自动重基覆盖这些新数据。宿主明确告知未同步，下一业务轮读取新版本；不为此自动调用模型。新建状态并写首次体验使用报告的 `create`，同次修改名称、简介、分类或规则使用报告的 `revise`，避免把自己的同次修订误当作外部冲突。

主观消息、助手回复和唤醒记录不再同时触发旧关键词加减。尚未补齐新时间规则的旧定义继续既有客观事件与时间算法；明确采用 `time_rules` 后，事件变化全部由模型语义回报，旧数值触发规则不再执行。语义报告写入当前绝对体验值，不重放输入事件，也不把已保存报告再当成一次刺激。

## 条件时间规则

模型增加新状态时必须填写完整的增加条件、每次间隔、增加量、减少条件、每次间隔、减少量和时间下降下限。示例结构如下；数字仅用于协议示意，不作为任何状态的默认值：

```json
{
  "increase": {
    "condition": "not_contacted",
    "reason": "一段时间没有收到联系",
    "interval_minutes": 1,
    "amount": 1
  },
  "decrease": {
    "condition": "custom",
    "reason": "这次交流让我感到想念正在缓解",
    "interval_minutes": 1,
    "amount": 1
  },
  "floor": 30,
  "contact_window_minutes": 10
}
```

条件选项只有 `always` 任何、`not_contacted` 未联系、`custom` 自定义。原因文字可以自由描述，文字本身不充当关键词触发器。数字快捷建议为 0 至 30，选择自定义时仍必须提交 JSON 数值，支持小数、零和更大的有限数值，没有 30 的上限。`floor` 也由模型填写，30 不具有特殊含义。

- 间隔为零或负数时暂停该方向；变化量为零时不变化。负变化量按有符号数计算，会反转所选方向，不静默改写输入。
- 时间经过后按比例结算，宿主不需要每分钟唤醒模型。两个条件同时成立时合计有符号速率，并在联系条件边界分段计算。
- `floor` 只阻止被动时间下降继续越过该值，不会把已经较低的体验抬高。模型仍可根据事件报告更低的值；实际状态始终受自己定义的 `min/max` 限制。
- 使用未联系条件时必须明确 `contact_window_minutes`：真实用户消息之后，在该窗口内不计作未联系，超出窗口后开始适用。窗口为零或负数代表零等待。没有真实联系记录时条件尚未知，不编造联系史。
- 联系使用实际持久化的用户消息及原消息时间；请求准备、重生成、助手回复和自动唤醒不能刷新联系时间。`global` 状态跨同助手窗口，`session` 状态只看本会话。
- 自定义条件由模型用 `time_conditions:{increase:true/false,decrease:true/false}` 报告成立或结束，只能填写规则本身选了自定义的方向。尚未报告的条件不计时；省略已有方向保留原状态。
- 条件切换先按旧条件结算到报告提交时，再影响未来。改名或调速保留含义未变的条件；原因含义改变后清除旧成立标记，等待模型重新报告。

新规则一旦定义，就代替旧半衰期、时间漂移及客观事件的数值触发，不叠加两套算法。存量状态没有 `time_rules` 时显示“新时间规则未定义，原演化规则继续生效”；其当前值和历史不重设。旧算法在明确修订前继续如下行为：

- `halfLifeHours=0` 时，按每小时漂移线性变化；漂移也为零时保持原值。
- 半衰期大于零时，按该维度的半衰期向平衡点接近。没有持续漂移时平衡点是基准；存在持续漂移时平衡点为 `baseline + rate × halfLifeHours / ln(2)`。
- 旧参数仍可在该状态的折叠规则中查看，历史版本保持原样。

具体状态的涨落参数全部交给模型制定，程序不根据截图预填“思念 30”或任何类别、速度。情绪数值淡化不会自动把 `unresolved` 改为已解决，也不会把欲望变成选择或行动。

## 按状态浏览与隐私

当前页按驱力、情感、情绪、心理筛选，存量未分类状态单独保留待分类入口。列表卡片只保留名称、数值、简短标志与紧凑趋势；点击状态打开自己的详情。详情显示完整简介、体验和变化时间线，演化规则和版本历史默认折叠，展开后完整显示。

曲线按真实记录定位，变化点可以选择查看时间、前后值和可展示的事件原因。新时间记录保留时间区间与规则原因；事件变化保持实际跳变，不捏造平滑波动。历史被隐私过滤时中断连线，不根据相同数值猜测中间没有发生变化。没有变化时曲线仍可能为水平线。

主体可使用私密状态进行内部判断，但可见性不因新版本改为公开就追溯放开旧体验。状态、历史体验和变化分别携带披露标志，继承字段保留来源版本的隐私；自定义条件的两个方向分别记录来源，不能因重报一个方向公开另一个方向。观察副本继续按当前及历史边界过滤。隐私标签不改变用户授权或工具权限。

## 插件处理链的支持边界

语义状态回报属于宿主持有角色、会话和版本的原生对话事务。普通 `message_processing` 插件可以替换整条生成链，也可以把任务交给多个规划、执行或总结模型。插件产生文本不代表这些内部模型拥有当前助手的主体身份，因此通用插件本轮不接入语义状态回报提交。

`AIMessageManager` 给插件传递原来的 `messageContent` 和 `chatHistory`，不会把私有状态附件塞进插件的问题文本，也不会为插件探测或执行准备可写 frame。插件文本不经过主体状态解析；没有宿主绑定时，协议标签示例仍是普通文本，不据此猜测身份或写入状态。已有消息、工具事实记录继续按各自原有链路运行。

### 用户消息和自主唤醒

- 用户消息默认经 `MessageProcessingDelegate`、`AIMessageManager` 进入原生 `EnhancedAIService`。只有已安装插件明确匹配并接管普通交互时，才使用插件生成链。
- 系统自动唤醒、手机感知唤醒以及自主学习中的 exploration/reading 都由 `CompanionRuntime.evaluate` 创建宿主持有的回合。`AIMessageManager` 通过 `CompanionRuntime.isWake(chatId)` 识别该回合，在调用插件探测之前固定走原生链，保持角色绑定和成功结束后的单次提交。
- 这一选择依据宿主回合状态，不依据模型输出或问题中的“唤醒”字样。插件不能通过修改输入文本改变主体归属。

仓库提供的 deepsearching 示例把 `ai_planning` 开关默认设为关闭。用户主动打开后，它会匹配普通非空输入，并调用多个独立内部会话完成规划、子任务和总结；这一条被接管的普通交互不提交新的主体语义状态报告。自主唤醒不会被这个开关抢占，也不会消耗该次普通交互的插件选择。

### 插件未来接入的要求

插件若需要提交主体状态，必须另行定义可验证的最终主体表达阶段、宿主提供的写入绑定，以及区别于内部子模型的明确成功与取消信号。仅传一个角色名、让插件回显 JSON，或者把 `collect` 正常返回视为整个插件成功，都不足以建立该事务。

当前实现没有为插件增加模型调用，也没有把规划或总结模型的状态当作助手体验。原生请求与通用插件的边界应保持明确，不能靠转发私有报告文本来绕过宿主绑定。
